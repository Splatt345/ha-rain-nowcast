# PINNED, not floated, and numpy/scipy are the reason.

# Every accuracy number this add-on claims (CSI 0.4043 held-out, the CRPS
# baseline, the measured reliability of `rain_chance`) came from the research
# repo's venv on numpy 2.2.6 / scipy 1.15.3. With `>=` bounds a rebuild shipped
# numpy 2.5.2 / scipy 1.18.1 instead - a forecaster nobody had scored, changing
# silently and only on rebuild. pysteps' cascade decomposition and AR(2) update
# run entirely through numpy/scipy FFT and filtering, so that is exactly where a
# quiet numerical change would land.
#
# Bump deliberately and re-run the research repo's evaluation, rather than by
# editing a bound here. Python differs from the research venv (3.12 here, 3.10
# there) because Home Assistant's base image sets it: a known, accepted gap.

# CPU-only torch for the SmaAt-UNet second opinion. The CPU index is not
# optional: the default PyPI wheel pulls the whole CUDA runtime and adds
# multiple GB to an image that has no GPU to use it with. Inference is 0.6 s per
# cycle on 4 CPU threads against STEPS' ~12 s, so the cost here is image size
# (~200 MB), not runtime.
